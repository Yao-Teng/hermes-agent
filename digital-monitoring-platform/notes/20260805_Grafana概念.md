# Grafana 概念 — 即時運營監控與告警（數位監控平台第二支柱）

- 日期：2026-08-05（主題輪替 index=1 → Grafana）

- 定位：六支柱中的「**現在發生什麼事**」——秒級即時監控 + 告警引擎；資料流過即顯示，不適合深層聚合分析（那是 Superset 的事）

## 1. 今日主題與概念摘要

### 一句話定位
Grafana = **儀表板 + 告警引擎**，時間序列（metrics/logs/traces/profiles）為主的即時可視化平台；「資料流過即顯示、問題發生即告警」。

### 核心概念（採官方術語，2026-08 檢核）

1. **Datasource（資料源）**：連到「存放資料的後端」的抽象（Prometheus、Loki、PostgreSQL、InfluxDB、Elasticsearch…）。Grafana 對資料源下查詢取得資料，再於 dashboard/Explore 視覺化。核心資料源按用途分五類：
   - **metrics/time series**：Prometheus、AWS CloudWatch、Azure Monitor、Google Cloud Monitoring、Graphite、InfluxDB、OpenTSDB
   - **logs**：Loki、Elasticsearch
   - **traces**：Tempo、Jaeger、Zipkin
   - **profiles**：Pyroscope、Parca
   - **SQL 資料庫**：PostgreSQL、MySQL、MSSQL
   - 另有三種**特殊資料源**：`Grafana`（隨機 walk 測試資料）、`Mixed`（同一面板內查詢多個資料源）、`Dashboard`（把同儀表板另一面板的結果當資料源）
   - 每個資料源有專屬 **query editor**；資料源管理在 **Connections > Data sources**，僅 org admin 可新增/移除
2. **Panel（面板）**：dashboard 的基本積木 = **query + visualization**。視覺化從 time series、bar、gauge、stat、table 到 heatmap、3D charts。
3. **Dashboard + 模板變數（Variables）**：變數是「值」的佔位符，可用於查詢、面板標題、連結；顯示為儀表板頂部下拉，觀眾可自行切換（如店別、站點、時間範圍）而不需編輯。**8 種變數型別**：Query（值來自資料源查詢）、Custom（手動固定清單）、Text box（自由輸入）、Constant（觀眾不可改的常數）、Data source（切換資料源實例）、Interval（時間分組間隔）、Filters（dashboard 級 key/value 過濾）、Switch（兩個值切換）。變數值預設同步到 URL（`var-<varname>=value`），可用 `skipUrlSync: true` 關閉。另有內建 **global variables**（目前時間範圍、儀表板名稱、org、登入使用者）。核心價值：**single-source dashboards**——一間店一個儀表板 vs 一個儀表板用變數切所有店，減少重複與維護成本。
4. **Alerting（告警）**：**建立在 Prometheus alerting model 上**。完整管線：
   - **alert rule** = queries + expressions（選資料）＋ **condition**（觸發門檻）＋ 評估間隔（多頻繁跑）＋ **`for` 持續時間**（條件要維持多久才算觸發，避免瞬時抖動誤報）
   - 週期評估 → 每個 alert rule 可產生**多個 alert instance**（每條 time series 一個，multi-dimensional——單一規則監控所有 CPU）
   - firing/resolved 狀態才送通知 → 直接送 **contact point**，或走 **notification policies**（樹狀結構、根為 **Default policy**、用 **label matching** 路由到不同團隊/服務的 contact point；可設 **grouping** 把相關告警群組成單一通知減噪）
   - **silences**（一次性暫停，如維護窗口）與 **mute timings**（定期暫停，如週末晚間）只暫停通知、不中斷規則評估
   - **recording rules**：預先計算高成本/常用查詢，結果存成新 time series，供儀表板與告警重複使用
5. **Explore**：免建 dashboard 的 ad-hoc 查詢與即時分析起點；支援 logs/traces 整合、Correlations（跨資料源關聯）。
6. **Provisioning as code**：用 YAML（或 Terraform）定義資料源與儀表板，啟動時套用，**GitOps 友善**。重點語法：`deleteDatasources`（先刪清單）、`prune: true`（從 provisioning 檔移除即自動刪資料源）、`$ENV_VAR` 環境變數取代（注意 `$` 逸脫 `$$`）、`jsonData`（一般設定）vs `secureJsonData`（密碼等加密儲存）、多實例部署用 `version` 欄位避免舊設定覆寫新設定。
7. **PostgreSQL 資料源（平台最關鍵）**：內建 plugin 免安裝；支援：
   - **Time series queries**：內建時間分組 macro
   - **Table queries**：任意 SQL 的表格結果
   - **EXPLAIN**：直接在 query editor 看執行計畫
   - **Template variables**：內建變數查詢編輯器
   - **Annotations**：把 Postgres 事件疊到圖上
   - **Alerting**：⚠️ **僅限 time series 格式查詢**
   - **TimescaleDB toggle**：開啟後支援 `time_bucket`（時間序列擴充整合！）
   - 連線走 **PGX driver**，支援 int/numeric/text/timestamp/timestamptz/bool/**json/jsonb**/enum 等型別；支援 PostgreSQL 9.0+ 及 RDS/Aurora/Azure/Cloud SQL 等相容 DB

## 2. 架構 / 流程說明

### Grafana 在數位監控平台的定位
```
PostgreSQL 數位資料倉庫（metrics 層 / TimescaleDB hypertable）
        │  PostgreSQL datasource（內建、macro、EXPLAIN）
        ▼
   ┌─────────────────────────┐
   │  Grafana（秒級即時 + 告警）│
   │  ├─ Dashboard：模板變數切店別/站點（Query 變數從倉庫撈店清單）│
   │  ├─ Panel：time series / gauge / stat / table              │
   │  └─ Alerting：SLA 違規、爐口利用率、單量異常               │
   └────────────┬────────────┘
                │ 告警 Webhook（contact point: webhook）
                ▼
        n8n 自動化閉環（通知/開單/補救工作流）
```
> 對比 Superset：Grafana 管「現在發生什麼」（秒級 + 告警），Superset 管「過去發生什麼、為什麼」（深度分析）。兩者共用同一個 Postgres 倉庫，不互斥。

### Alerting 管線文字圖
```
[Alert Rule] queries + condition + 評估間隔 + for 持續
      ↓ 週期評估
[Alert Instances] 每條 time series 一個（multi-dimensional）
      ↓ firing / resolved
[Notification Policy] 樹狀、label 路由（根 = Default policy）
      ├─ grouping（群組減噪）
      ├─ silences / mute timings（暫停通知不暫停評估）
      └─ → [Contact Point] Email / Slack / Telegram / Webhook / PagerDuty
                  ↓
          n8n / IRM（自動行動）
```

### 餐廳營運儀表板概念（Postgres 為單一資料源）
```
Dashboard「餐廳營運即時總覽」
  ├─ 變數：$store（Query: SELECT DISTINCT store FROM marts.store_daily）、$interval
  ├─ Panel 1: 今日單量 time series（$store 過濾）
  ├─ Panel 2: 爐口利用率 gauge（門檻 85% 變色）
  ├─ Panel 3: 營收 stat / table
  ├─ Panel 4: 庫存異常 table（JSONB 展開）
  └─ Alert rule: 爐口利用率 > 90% for 5m → webhook → n8n 通知值班
```

## 3. 實用指令（Docker / provisioning）

```bash
# Docker 一鍵起（官方映像，預設 port 3000）
docker run -d --name=grafana -p 3000:3000 grafana/grafana
# 開啟 http://localhost:3000（admin/admin，首次要求改密碼）

# 本機測試資料源：TestData（內建，產生隨機 walk）→ 學習面板/變數零成本
```

Provisioning 資料源 YAML（GitOps 風格，放 `provisioning/datasources/`）：
```yaml
apiVersion: 1
prune: true
datasources:
  - name: PostgresWH
    type: postgres
    access: proxy
    url: postgres:5432
    user: grafana_ro
    database: digital_warehouse
    isDefault: true
    jsonData:
      postgresVersion: 1500
      timescaledb: true          # TimescaleDB toggle → time_bucket 可用
      sslmode: disable
    secureJsonData:
      password: $PG_GRAFANA_PASSWORD   # 環境變數取代（密碼加密儲存）
```

## 4. 與「餐廳營運監控」的關聯
- **單一真相源**：Grafana 直接查 PostgreSQL 倉庫的 marts/metrics 層，不做 ETL、不改資料——「看板」與「倉庫」解耦
- **即時單量/爐口利用率**：Time series + gauge 面板，模板變數 `$store` 一板切全店
- **SLA 違規告警**：alert rule（`for` 持續時間防抖動）→ contact point（webhook）→ n8n 自動通知/開單（閉環）
- **TimescaleDB 整合**：metrics 層用 hypertable + Grafana 的 TimescaleDB toggle，秒級查詢效能關鍵
- **營運事件疊圖**：Postgres annotations 把 POS 促銷活動/庫存補貨事件疊到單量曲線上，找因果
- **儀表板即程式碼**：provisioning YAML 版控，跟 dbt models 一起進 Git——「儀表板、轉換、倉庫 schema 全部可重現」
